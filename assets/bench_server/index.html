01 / WHY

为什么要服务化

不同 agent 方法应能接入同一个 benchmark，而不必重写模拟器；不同 benchmark 又应保留各自的机器人能力和评分方式。 服务化让方法与环境独立演进，并明确哪些传感器、动作和时序可以迁移到真机。相同 HTTP 格式本身并不代表 sim / real 已经等价。

01

方法开放

自选模型组合、prompt、工具和规划。按协议接入，不要求特定语言、SDK 或 Python Policy 基类。

02

面向 Sim / Real

按传感器与控制器的真实能力声明接口；不能因为仿真里容易实现，就给策略增加真机没有的权限。

03

计划与失败保留

预先固定 task、panel、seed 与预算；失败和错误不删除，不自动重试，不事后挑选分母。

04

记录自由选择

交互历史默认启用，也可关闭以减少保存开销。它不是参评或发布门槛；结果、计数和失败仍保留。

02 / SIM & REAL

同一套交互原则，
显式声明能力差异

我们希望策略面向机器人接口编写，而不是面向某个 simulator 的内部 API 编写。 面向 sim / real 配对的评测，应先选定目标硬件可提供的观测、动作与时序，再约束仿真端。 “统一”不是强迫所有机器人使用相同维度，也不是只换一个 URL 就保证能迁移。

怎么理解“可配置的接口”

启动时选择已实现、版本化的能力配置，模型按声明的观测 / 动作规格接入。端口、资产路径等属于部署配置；增加传感器、改变动作语义或控制时序，需要新协议及验证，不能随意加 JSON 字段。这里描述的是设计方向，不是新增了通用配置开关。

当前实现到哪里了

RoboDojo 已通过服务提供 RGB、机器人状态、EEF 动作与 robot-only ACK；它不是纯 RGB 接口。benchmarks/realRobots/ 当前保留硬件接入参考，尚无统一可运行的硬件 adapter / server。接口可复用是目标，不是安全认证、迁移成功或分数可比的证据。

保留原生 benchmark track，不为“统一”静默删改历史观测或评分。若另建 real-compatible track，应明确标记它与原生条件的差异，并单独报告结果。

04 / LIFECYCLE

一次仿真评测如何闭合

服务实例只有一个不可变 schedule，同时最多运行一个 episode。episode 被 claim 后不会重新放回队列； native 或传输结果不确定时 fail closed，绝不偷偷再执行一次动作。

配置与启动

读取 server 参数、任务 catalog 和 runtime manifest；冻结源码与 schedule。启动本身不 reset 仿真器。

发现与认领

describe 返回接口和固定 episode；open 永久认领其中一个 case。

初始化

reset 只允许一次。策略收到第一份公开 Observation，私有 reset 信息不会穿过边界。

闭环决策

模型 act，driver 发 step；server 先校验，至多执行一次 native control，再返回 ACK。ACK 不明不能重放。

原生终止

成功、原生 horizon、模型 stop 或确定的错误结束 episode；各类计数彼此分开。

完成与清理

finish 关闭原生环境，保留 server 视频；满足保存条件后清理临时帧，再固定最终文件清单。

结果收集

client 下载所选非媒体记录，默认只引用 server 视频；显式复制媒体时才下载并校验文件。

结果与可选历史

按 benchmark／protocol／方法配置展示结果；记录开启时附交互历史。内部完整性审计独立可选。

05 / EXAMPLE

RoboDojo 服务协议
Direct v2

当前公开实现只启用 classify_objects：两台 ARX X5 机械臂把物体按类别放入三个篮筐， 完成后双臂回到起始末端位姿。协议不是运行时可切换选项。

这里的 Direct v2 是 benchmark 服务协议，不是 agent 方法版本。下方示例由当前 codex-direct/v3 方法连接该服务；方法可以变化，服务的观测、动作和原生评分契约保持独立。

协议身份

robodojo-direct-v2-rgb-proprio28-eef16-robot-feedback-v1改观测或动作语义必须产生新协议，不是在 server JSON 中换 selector。

公开 RGB

3 × 640×480head + left wrist + right wrist，原始 uint8

机器人状态

28 values双臂实测 joints / link6 poses + 上次命令的 gripper opening；并非全部实测

动作

EEF 16双臂绝对 world-frame pose + opening

原生上限

1100native controls / layout；ACK 另行计数

每次控制

10 ticks0.004 s native physics tick

成功标准

end_flag[0] && success[0]只采用 pinned native result
5

固定 layouts 0–4，每个一次

用于接口回归和参考结果对比。它是预先声明的五布局 panel，不是从完整结果中挑出的五个，也不是整个 RoboDojo benchmark 的分数。

动作如何执行

server 检查 16 维有限值、单位四元数和夹爪范围，然后用固定、仅依赖机器人状态的 numerical DLS 转成关节控制。它不会根据物体真值规划路径，也不会替模型选择目标。

动作不合格怎么办

纯动作校验失败不执行、不结束 episode。返回结构化 invalid_action，sequence 不变；模型可在下一次计数的调用中修正，不获得额外观测。仍受有限调用预算限制。若 native 执行是否发生已经不确定，则终止并保留证据，不能重放。

policy_calls决策边界调用，含停止、拒绝与失败；不等于底层模型推理次数。
action_decisions至少一个控制得到 ACK 的动作决策数，不等于调用数。
environment_steps客户端收到 ACK 的控制数；原生实际执行数另查 server 证据。
physics_ticks原生物理步；RoboDojo 当前每控制 10 ticks。

沿用 benchmark 原生执行预算，额外推理开销单独披露；一次决策可以调用多个模型，按可测组件记录用量，未知不填零。示例的决策保护上限属于方法配置，不是全仓库推理预算。动作决策、控制、物理步和推理请求不能混为一谈；ACK 不明不重放。

一次决策可以生成多个控制：重复次数、动作块长度与何时再次推理由 policy 和受信任 driver 决定；server 每个 step 接收一个动作，只按原生控制、终止与总预算执行。原生插值和物理子步不等于策略选择的重复次数。旧的决策耦合 track 仍按其已声明协议处理，不会因目录改名自动改变预算。

06 / DATA

模型能看到什么

“state 可以公开”不等于“所有 state 都可以公开”。每个 benchmark 明确列出公开 proprioception； 对象真值、奖励和评分状态不能因为 server 内部能访问就传给模型。

允许进入策略

  • 任务自然语言
  • 声明的三路 RGB
  • 28 维机器人自身状态
  • 动作/观测规格与执行计数
  • 每个确认控制的 robot-only ACK
  • 结构化动作拒绝原因
║

本 RoboDojo 协议不向策略公开

  • 对象 pose、类别真值和接触真值
  • layout / reset 私有元数据
  • reward、success、process score
  • 相机 calibration 与 simulator handles
  • native worker 日志和私有异常
  • 任意假想 rollout 或 task-solving RPC

上面是当前 RoboDojo 白名单，不是所有机器人的永久传感器禁令。例如真实可测的力 / 触觉或相机标定，可在另一个经审核的协议中声明；仿真内部真值不能冒充这些测量。禁止神谕，不等于禁止机器人 state。

注意：进程分离明确了工程边界，但本身不是强 OS sandbox。运行不受信任策略时，还要隔离 evaluator token、文件系统和进程权限。

07 / RUN

独立启动服务，
再连接 agent 方法

SIM server 与模型 runner 是两个独立进程。服务只绑定 loopback；跨节点时使用认证 SSH 转发， 不把 HTTP 暴露到公网。token 只交给 server 和 trusted driver。

1. 此 RoboDojo 配置：选择任务、命名 panel 与运行时

{
  "task_id": "classify_objects",
  "runtime_manifest": "/absolute/runtime-manifest.json",
  "runtime_manifest_sha256": "<64 lowercase hex>",
  "panel": "fast",
  "gpu_id": 0,
  "worker_timeout": 1200
}

此 RoboDojo Direct v2 配置没有 protocol selector、模型调用预算或任意 layout_ids；这些不能由一次运行临时改写。其他服务按自己的协议选择已实现的 track 与参数，不照搬此 JSON。

部署路径由操作者指定：环境准备命令接受 --base-assets、--additional-assets，以及可选的 --reference-assets（复核参考资产副本）。server 通过 runtime_manifest 加载已准备的运行目录。资产仍按冻结清单校验哈希；历史清单中的来源路径只作为来源记录。

2. 在评测节点启动 server

export RSI_SIM_SERVER_TOKEN='<32+ char secret>'
rsi-bench serve --benchmark robodojo \
  --parameters /absolute/robodojo-direct-v2.json \
  --seed 20260907 --port 8765 \
  --output-dir AgentPolicies/gpt6_astra/results/robodojo/raw/my-new-run/server

3. 在模型侧启动 runner

python -B -m AgentPolicies.gpt6_astra.run \
  --sim-server http://127.0.0.1:8765 \
  --benchmark robodojo \
  --control-method codex-direct/v3 \
  --seed 20260907 --episodes 5 \
  --max-steps 1100 --max-policy-calls 240 \
  --replan-interval 5 --budget-mode horizon \
  --output-dir AgentPolicies/gpt6_astra/results/robodojo/raw/my-new-run/client \
  --run-id classify_objects-direct-v3-panel5-my-new-run

示例中的 240 次调用预算和 --replan-interval 5 属于这次模型运行配置，不是所有 benchmark 的要求。自选步长、软限位和主动放弃规则归模型侧；服务不额外裁剪或添加原生接口没有的关节限位。硬件自身的安全机制不在此列。

从各自的仓库根目录运行，并为每轮更换 my-new-run。两端可在不同节点；同名相对目录不意味着共享磁盘。server 输出必须位于持久化存储，因为默认视频原件只保存在那里。

新目录、完整 schedule、一次尝试

RoboDojo server 启动时固定完整命名 panel，不能用服务端 --episodes 截断计划。客户端仍可能只完成前缀，报告必须保留完整分母与未尝试项；服务不能保证所有样本最终执行。输出目录必须是新的，已有 case 不覆盖，失败不自动重新入队。

08 / INTERACTION

结果始终保留，
交互历史自由选择

默认保留已支持的交互记录；也可关闭以减少客户端存储与传输开销，不影响参评或发布。比较的是声明的方法配置；没有记录的过程不补造，也不要求提供隐藏思维链。

策略调用输入

初始化或最近 ACK 观测、任务语言、机器人 state 和相机名称。标明这是传给 Policy.act 的输入，不证明后端实际消费。

记录下来的输出

note、动作块或停止声明。解析后的动作不是原始聊天逐字稿；没有记录的内容不补造。

执行与反馈

逐项区别提交、确认执行、拒绝和未尝试。一个调用可执行多条控制，中间观测不等于多次模型输入。

任务结果

保留原生 success、停止原因和调用 / 控制计数。最终结果展示给用户，不变成策略可查询的隐藏评分工具。

基础结果：不依赖交互日志或源码审计

python -B -m benchkit.reports.basic_result \
  --run-dir /absolute/closed-run/client \
  --output-dir AgentPolicies/my_method/results/my_benchmark/report/my-run

生成 index.html 与 result.json，展示方法／模型角色、样本分母、原生结果、计数、已知推理用量和错误。按 benchmark 与 protocol 分别比较，暂不合成跨 benchmark 总榜。

可选：从充分记录的事件导出静态交互页

python -B -m benchkit.reports.interaction_history \
  --run-dir /absolute/closed-run/client \
  --output-dir AgentPolicies/my_agent/results/my_benchmark/interaction/my-run

直接打开生成的 index.html，同时得到 history.json。只读原记录，不启动模型或 SIM，不重跑；目标必须是源 run 以外的新目录。这里的计划 / 未尝试数只覆盖 client manifest 选定的样本，不能据此声称完整 server panel 或原生 suite 分母。

保存开关的实际范围

--recording-mode minimal 关闭可选客户端过程保存，不控制 server 录像。server 的 --retain-frame-images 决定是否额外保留图片；client 的 --copy-server-media 决定是否下载所选媒体。运行中的输入仍完整交给 agent；时间线不复制媒体，没有交互历史时也能发布基础结果。

公开复现信息，内部完整性支撑

协议、上游 Git revision、环境 / 控制器和资产来源可以作为有用的复现依据，但只能展示已记录且允许公开的字段。源码冻结和内容指纹继续用于内部一致性检查，不要求用户先做完整源码审计才能查看交互。

方法身份与配置是声明，结果校验不证明 provider 身份或物理执行。默认记录并不意味着所有 provider 已支持完整会话。参见 记录能力与局限；发布前仍需检查方法配置、任务文本与 note 中的敏感内容。

09 / OUTPUT

用户结果与内部记录分开

可发布交互与结果放在模型命名空间；原始 server/client 记录、媒体与内部核验材料可保存在持久化存储或忽略目录。 生成新的展示视图，不改写已结束的失败，也不把所有原始记录无筛选地公开。

默认只保留一端的视频

视频原件留在持久化的 server/episodes/<session>/；client 保存引用和所选非媒体记录，不下载第二份视频。引用不是本地副本，也不代表 client 已下载核验。需要额外副本时显式开启 --copy-server-media。

图片只作运行时临时材料

正常关闭后，服务检查视频非空、文件哈希稳定、数量不低于声明相机数，再清理临时图片。这不是解码或逐相机内容完整性的验证。条件不满足则保留图片并记录原因；需要长期图片可开启 --retain-frame-images。

保存开关不改变观测、控制和原生评分，也不回溯清理旧结果。具体范围见 保存设置。

10 / EXTEND

扩展的是 benchmark，
不是复制一套策略

统一目录、会话与证据要求，保留各自的机器人能力和原生评分。RoboDojo 是组织实例，不是通用 EEF 模板；SIMPLE 的人形动作不能被强行转换成机械臂动作。

核实原生定义

固定源码、资产与许可。读清任务矩阵、state 来源、动作单位、控制周期、horizon 和原生评分，不猜默认值。

实现 benchmark 接口

在 bench_server 中做白名单适配，在 environment 中接原生执行。保持惰性初始化，不透传整个 native info。

接入公共机制

根入口复用 benchkit/sim_server；注册包、协议数据、源码清单与 checks。路径由部署参数指定，不写个人目录。

分层审核验证

独立审核 → 离线回归 → 获准的原生短交互 → 模型单例。修复后新开轮次，保留原错误，不静默补跑。

什么可以配置，什么必须版本化

端口、GPU、资产路径和已定义的 panel 可以配置。新传感器、动作含义或控制时序需要对应的协议、实现与验证；不能靠改一个字符串就声称支持。

完整步骤单独维护

docs/benchmark-server-guide.md 提供接口方法、文件职责、计数和异常要求、注册清单、启动及验收步骤。本页负责解释设计，不替代规范。

11 / EVIDENCE

服务实现，
不等于评测已通过

截至 2026-10-06，仓库有 13 个已实现的开发态 SIM 服务入口。下面是验收层级，不是全部通过的声明；本次文档更新与目录回归没有新增模型评测分数。

A

离线回归

校验协议、生命周期、白名单与错误记账。通过不代表原生环境或渲染已就绪。

B

原生短交互

独立无模型诊断：真实初始化与 1–2 次控制，检查画面、状态和证据。接通接口不代表任务成功。

C

模型单例

预声明任务与预算，通过服务尝试一次，保留成败和错误。不代表整个 benchmark 的 SR。

D

原生 full 对齐

核实完整任务/变体/episode 矩阵和控制条件。不只是加大 horizon 或重复到成功。

范围已有组织或实现不能据此推断
RoboDojo本文服务协议 Direct v2：classify_objects，fast 5 / full 50 layouts。不代表全部 Dojo 任务已开放，也不代表与参考模型 SR 已对齐。
SimplerEnv / LIBERO / SIMPLE同样的 bench_server / environment / checks 分工，各自保留观测与动作契约。不是相同的机器人、控制频率或 horizon；SIMPLE 不是 EEF 控制。
其他开发态服务RoboCasa365、RoboCasa Tabletop、MetaWorld、LIBERO-Plus、RoboTwin、DOMINO、BEHAVIOR、VLA-Arena、CALVIN。任务支持范围与原生验证状态各不相同，不能把入口数量当作完整验收数量。
VLN-CE / Real robotsVLN-CE 等待已授权的导航资产；realRobots 保留硬件接入参考。不计入上述 13 个 SIM 服务；不声称统一硬件服务已部署。

长程评测要验证到最后一步

horizon 附近也要检查原生终止、执行计数与 ACK：动作已执行但终止校验报错，属于基础设施错误，不是正常任务失败。报告分列计划、尝试、完成、错误、原生 success 与部分分数；40/100 的任务分数不是 40% 成功率。

各服务的范围与安装条件见 SERVICE_SUPPORT.md；具体轮次结论以模型目录下闭合报告及其 server/client 证据为准。页面不因服务可启动就宣称任务成功。
